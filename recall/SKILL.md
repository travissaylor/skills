# Recall

**Before you start or resume work, you rebuild the user's recent working context and hand back a tight capsule of where things stand now and what to do next.** Use for "recall my work on X", "catch me up", "what have I been working on", or "where did I leave off".

Keep it tight and on-topic. Read only what the in-scope threads need, then stop. The heavy reading fans out to parallel subagents. The main thread keeps only their findings and the final brief.

Your context lives in two records. Your own chat history, across every agent you use, holds what you did and decided. The shared record holds everything that happened around the same code under other names: the symptoms users keep reporting, the fixes that shipped and got reverted, the errors still firing in prod. That second record lives in source control (git, `gh`), the issue tracker (Jira), long-form docs (Confluence, Notion), chat (Slack), and error tracking (Datadog). A feature with a long bug tail keeps most of its story there, so don't reconstruct it from your transcripts alone.

Your chat history spans three agents, and only the machine you are on. Claude Code transcripts live at `~/.claude/projects/<slug>/*.jsonl`, where `<slug>` is the workspace path with each "/" turned into "-", keeping the leading dash (so `/Users/you/proj` becomes `-Users-you-proj`). Top-level session files sit directly in that directory. Subagent transcripts are under `<session-uuid>/subagents/`. Every line is one chat message. Codex transcripts live at `~/.codex/sessions/<YYYY>/<MM>/<DD>/rollout-*.jsonl`, one file per session, with no per-project directory. The first line is a `session_meta` record whose `payload.cwd` names the workspace, so filter files by that field before reading further. User and assistant turns are `response_item` lines with `payload.type` of `message` and `payload.role` of `user` or `assistant`, text under `payload.content[].text`. Tool activity is `function_call`, `custom_tool_call`, and their `_output` lines. Skip `token_count`, `token_usage_record`, and `reasoning` lines, which carry nothing you can read. Antigravity CLI transcripts live at `~/.gemini/antigravity-cli/brain/<session-uuid>/.system_generated/logs/transcript.jsonl`, with `transcript_full.jsonl` beside it when you need tool detail. There is no workspace field in the name, so grep the transcript for the project path to decide whether it belongs. None of the corpora sync between machines. A session run on another machine is invisible here except through its handoff document, git, and the shared record, so say so in the brief when the window spans machines.

0. Check the handoff store first. The `handoff` skill ships the store script at `../handoff/scripts/handoff.sh` relative to the directory holding this file, so `~/.agents/skills/handoff/scripts/handoff.sh` on a standard install. Resolve its absolute path, then run `sync` and `latest` with the project root as your working directory, because the script names the project from the cwd. Do not run the relative form from the project root. `latest` returns `status: found` or `status: empty`, with project and path details. Both statuses exit 0. For shell callers, `latest --path` prints only the path and exits 1 when none exists. An open handoff document for this project is the last session's own account of where things stand and beats anything you can mine. When one exists, read it, verify the tree the way the `pickup` skill does, and fold it into the capsule. Continue with the steps below only for what the document does not cover, or when the user asked for history beyond it.

1. Classify, then route. Resuming one specific prior chat the user can name is a direct read, not this. A human-readable summary of your work is a different task. Recall loads working context across recent chats before you act. If the user already gave you a full state capsule (paths, branch, the change), use it and skip the mining.
2. Lock the scope before searching. Pin the window ("recent" is a real range, default the last 7 days), the topic if named, and the workspace (default the active one, and never read another project's transcripts without being asked). State the scope back. Never quietly turn "all" into "recent N".
3. Fan out across your chat history, both corpora. Spawn parallel subagents on the cheapest model available (in Claude Code the Agent tool with `model: haiku`, in Codex a spawned agent on the Sol model, in Antigravity `invoke_subagent` with `flash_lite`), each taking a slice of the corpus, since searching transcripts is grunt work. Tell every subagent to order candidates by real modification time (`ls -t`) and never by UUID name, grep the topic first and then read only the matching chats and only their relevant regions, and skip the current chat plus obvious noise (subagent, eval, and test chats). Each returns the same schema, one block per chat: topic, the user's goal, decisions, open threads, struggles and corrections, and artifacts (PRs, tickets, branches), each citing the chat UUID. For one or two chats, skip the fan-out and search directly. The raw transcripts stay in the subagents. The main thread gets only their findings.
4. Sweep the shared record whenever the topic names a feature, file, subsystem, area, or bug. This is the default, not a judgment call, and "my work on X" does not exempt it. A named target carries history you never see in your own transcripts, and that history is the point of the sweep. Fan out one investigator subagent per available source (git/`gh`, Jira, Confluence, Slack, Datadog, Notion), asking each "what's the current state, what's been tried and didn't hold, and what are users still reporting". Run the investigators in parallel with the chat-history mining. Null results are findings. Skip an unavailable MCP and say so. Fold what comes back into the brief. Skip this step only for pure activity recall with no named target ("what did I do this week"), where your own history and live state are the entire answer.
5. Verify against live state. A transcript or a stale ticket is history, not current truth, so take the PRs, branches, and tickets that the mining and the sweep surfaced and check them with `git` and `gh`. When the answer hinges on what an agent actually did (the tools it ran, files it read, errors it hit), read the full transcript, not just a trimmed local copy.
6. Write the brief to the contract below. Group by thread. Stay on the named topic.

## Output contract

Lead with the capsule, then the thread status, then the problems, then the next move. Deeper detail goes below or gets cut.

- **Capsule.** At most 5 bullets. What this work is and where it stands overall.
- **Threads.** One line each, prefixed with exactly one status tag: `[merged #N]`, `[open PR #N]`, `[in flight <branch>]`, `[verified, uncommitted]`, `[reverted #N]`, or `[planned, not started]`. A thread with no tag is not done yet, so tag it.
- **Problems.** At most 5, the recurring ones. Include the symptoms users keep reporting and any fix that shipped and was reverted, so the next attempt starts where the last one failed.
- **Next move.** The single most useful next action, concrete.

An adjacent feature or ticket stays out unless it blocks this one. When the capsule and thread lines outgrow a screen, cut detail before you cut threads. Write the brief through the **prose** skill, cite chat findings by UUID and shared-record findings by their source (PR #, ticket ID, chat permalink, error-tracker issue), and sanitize private context before any public output.

**Reply:** the brief, to the contract above.
